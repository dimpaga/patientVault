|---|---|---|---|
| D-001 | 2026-10-23 | Base package and Maven groupId: `com.example.patientvault`. | Confirmed by the project owner. |
| D-002 | 2026-10-23 | Java 25 (LTS) with Spring Boot 4.1.2 (latest stable 4.x at the time of writing). | JDK 25 is installed; Boot 4 supports it. |
| D-003 | 2026-10-23 | Automated tests (unit, integration, Testcontainers, Playwright, module-boundary verification, CI test stages) are **deferred** and will be added after the feature steps have been reviewed. | Requested by the project owner. Acceptance criteria stay in the spec and will be covered later. |
| D-004 | 2026-10-23 | Implementation proceeds in the order of spec section 14 with small commits and a review checkpoint after each step. | Requested by the project owner. |
| D-005 | 2026-10-23 | `TextNormalizer` lives in the `search` module (spec 4.1 assigns normalisation to `search`), although the step-1 table lists it with the crypto kernel. | Keeps `crypto` free of domain logic; `BlindIndexer` takes already-normalised values. |
| D-006 | 2026-10-23 | The blind-index key is derived from `APP_BLIND_INDEX_KEY_ID` (default: first key in `APP_MASTER_KEYS`), not from the active key. | Rotating the active KEK (spec 6.2) must not force re-indexing; only an explicit blind-key change does, as the spec requires. |
| D-007 | 2026-10-23 | Values encrypted directly with a DEK carry the header key label `dek`; wrapped DEKs and user secrets carry the master key id. | The DEK has no version, and re-wrapping must not leave stale key ids inside field ciphertext. Header is authenticated via AAD. |
| D-008 | 2026-10-23 | Tink's `subtle` primitives (`AesGcmJce`, `AesGcmHkdfStreaming`, `Hkdf`, `PrfMac`) are used with raw derived keys instead of keyset handles. | Keys are derived deterministically from the env key ring (HKDF) and are never stored as Tink keysets; subtle classes are Tink's supported low-level API. |
| D-009 | 2026-10-23 | Stream ciphers take a `purpose` (`content`, `thumb`) that is mixed into the HKDF info and AAD. | Prevents a thumbnail ciphertext from being accepted as file content and vice versa. |
| D-010 | 2026-10-23 | `./dev run` generates local keys into the git-ignored `.dev-secrets.env`; no key is committed in `application-local.yml`. | Spec 7.4: no secret in the repository. |
| D-011 | 2026-10-23 | The audit API (`AuditEvent`, `AuditService`) was introduced in step 2 with a log-only implementation; the append-only table, trigger and audit page follow in step 3. | Identity needs to emit audit events now; the module dependency direction (identity -> audit) stays as in spec 4.1. |
| D-012 | 2026-10-23 | The htmx-spring-boot library is not used; `HX-*` headers are handled by small helpers (`LoginRedirects`). htmx 2.0.11, Bootstrap 5.3.8 and Bootstrap Icons come from WebJars with fingerprinted URLs (no CDN, no Node build). | Spec allows dropping the library if compatibility is uncertain; fewer dependencies. |
| D-013 | 2026-10-23 | A `dashboard` package (outside the module list) holds the dashboard controller. | The dashboard composes the public APIs of several modules, so it cannot live inside one of them. |
| D-014 | 2026-10-23 | `app_user.totp_last_step` was added to the spec schema. | Rejects re-use of a TOTP code within its validity window (replay protection). |
| D-015 | 2026-10-23 | Two-step login: the password step only stores a `PendingMfa` marker (5 min); the session is authenticated, with a new session id, only after the TOTP/recovery code. A user without a TOTP secret enrols at first login (QR as SVG, recovery codes shown once). | Spec 7.1: the session must not be authenticated until both steps pass. |
| D-016 | 2026-10-23 | `app.security.mfa.required=false` allows login without a second factor for users who have not enrolled, but there is **no enrolment from Settings** yet. | MFA is mandatory by default; an enrolment page in Settings can be added if the optional mode is ever needed. |
| D-017 | 2026-10-23 | Lockout: 5 consecutive failures lock for 15 min, each further block of 5 doubles it up to 8 h (`app.security.lockout.*`). Failed passwords, second factors, re-authentications and current-password checks on password change all count; a successful full login resets the counter; `LoginAttemptCleanupJob` forgets lockouts that ended over 24 h ago. | Spec 7.1 asks for progressive lockout; counting every credential check closes side doors. |
| D-018 | 2026-10-23 | Audit records for failed logins use actor `ANONYMOUS` and never the attempted username. | Users sometimes type their password into the username field; it must not reach logs. |
| D-019 | 2026-10-23 | The per-IP rate limit uses `request.getRemoteAddr()` with `server.forward-headers-strategy=native`. | Correct client address behind Render's proxy as long as the proxy is in Tomcat's trusted internal ranges; verify on first deployment. |
| D-020 | 2026-10-23 | Bootstrap and reset passwords force a password change before any other page (`MustChangePasswordFilter`); the flag is mirrored in the session. | Spec 7.1 (`must_change_password`). Recovery-code, re-auth, logout and static paths stay reachable so the flow cannot deadlock. |
| D-021 | 2026-10-23 | The request cache remembers only HTML GET navigations (not htmx partials, assets or favicon requests). | Otherwise the browser's pre-login favicon request becomes the post-login redirect target. |
| D-022 | 2026-10-23 | Deferred from step 2: notification-email setting and reminder preferences (step 8), PWA manifest/service worker (step 9), Spring Modulith/ArchUnit verification (with tests). | Features that depend on later modules, or on the test phase. |
| D-023 | 2026-10-23 | Step 3 was reduced to a light logging mechanism at the owner's request: request-id filter, structured JSON logging (production), MDC context and an access log. The append-only `audit_log` table, its trigger, the audit page and `AuditRetentionJob` remain open; `LoggingAuditService` stays the audit implementation until they are built. | Requested by the project owner; the audit API is unchanged so the table can be added without touching callers. |
| D-024 | 2026-10-23 | JSON logging uses Spring Boot's built-in ECS format, enabled by the `prod` profile; local development keeps plain text with the request and user id in the level field. | Spec 9.2 allows ECS or Logstash; text is easier to read locally. |
| D-025 | 2026-10-23 | The access log counts response bytes with a pass-through response wrapper instead of buffering, and logs the matched route template (fallback: path with ids masked). | Large downloads must stay streamed; paths must not carry identifiers. |
| D-026 | 2026-10-23 | Exception-message sanitising in error logs is postponed to the hardening step together with the log-hygiene test. | No patient data exists yet; the test that proves it comes with the test phase. |
